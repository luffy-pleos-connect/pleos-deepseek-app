# MOCA 평가 기준표 v1 — API·값·판정 기준 확정

- 작성: 2026-11-11
- 목적: 평가자용 기준표가 모호했던 부분을 **어떤 API에서 어떤 값을 받아 무엇과 비교해 통과/실패를 정하는지** 수준으로 확정한다.
- 원칙: **문서에 없으면 "문서에 없음"**, **SDK 바이너리로 확인한 것은 [AAR]**, **이 맥에서 돌려 확인한 것은 [실측]**.

## 0. 먼저 알아야 할 사실 — Pleos 문서의 한계

Pleos 공식 API Reference는 **메서드 이름과 시그니처만** 있고 다음이 없습니다.

- 반환값의 **단위**(kPa·bar·%·km)
- 값의 **의미**(`getLowTirePressure`의 Float가 저압 여부인지 압력값인지)
- **정상 범위**
- 실패 시 동작

확인 방법과 결과:
```
agent-browser open https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle/ai.pleos.playground.vehicle.api/tire/get-low-tire-pressure
agent-browser eval "document.querySelector('main')?.innerText"
→ "Tire / getLowTirePressure / checkWheelAreaCapabilities / 이전 / Toll / 다음" (본문 없음)
```

**그래서 이 기준표는 다음 순서로 근거를 삼는다.**
1. SDK 바이너리(AAR 2.3.2)의 타입·enum — 확실
2. 에뮬레이터 실행 결과 — 확실
3. 계획서가 정의한 계산 규칙 — 우리가 정한 것
4. **문서에 없는 값은 "미확정"으로 표시하고, 앱이 그 값에 의존하지 않게 설계한다**

## 1. API별 — 어떤 값을 받아 무엇에 쓰는가

### 1-1. 동력(POWER)

| 항목 | API | 반환형 [AAR] | 값 의미 | 앱이 쓰는 곳 | 판정 기준 |
|---|---|---|---|---|---|
| 엔진오일 | `Safety.getEngineOilLevelState` | `OilLevelState` (LOW/HIGH/NORMAL/ERROR/CRITICALLY_LOW) | enum 5종 | 동력 감점 | `NORMAL`→0, `LOW`→−40, `CRITICALLY_LOW`→−50, `HIGH`→−25, `ERROR`→**측정 불가** |
| 변속기오일 | `Safety.getTransmissionOilLevelState` | `OilLevelState` | 같음 | (이번 단계 미사용) | 미사용이면 **측정 불가**로 명시 |
| 경고등 | `Safety.getTelltalesInfo` | `Telltales` (`.telltales: List<TelltaleData>`) | type·state·color(Int)·priority·warningCount | 동력/제동/타이어/전기/안전 전부 | `state != OFF` 이고 해당 카테고리 type이면 감점 |

**판정 규칙 (확정)**
- `OilLevelState.ERROR`는 **감점하지 않고 측정 불가**로 처리한다. "정상"으로 처리하면 안 된다.
- 오일 API가 `IllegalArgumentException(property ID is not in carPropertyConfig list)`로 실패하면 **미지원**이다. [실측: 에뮬레이터에서 실제로 이 예외가 난다]

### 1-2. 제동·조향(BRAKE_STEERING)

| 항목 | API | 반환형 [AAR] | 값 의미 | 판정 기준 |
|---|---|---|---|---|
| 브레이크액 | `Safety.getBrakeFluidLevelState` | `OilLevelState` | 오일과 같은 enum | 오일과 동일 규칙. **HIGH가 나오면 데이터 이상**이므로 "센서 확인 필요"로 표시하고 감점은 −25 |
| 경고등 | `getTelltalesInfo` | 위와 같음 | ABS·ESC·MDPS | RED −50 / YELLOW −25 |

**확정 사항**
- 브레이크액 반환형은 `OilLevelState` 다. [AAR] 문서에는 이 사실이 없다.
- **ABS가 RED인지 YELLOW인지는 미확정**이다. G0에서 주입 실패. 그래서 앱은 `TelltaleColor`가 아니라 **`color: Int`를 매핑 테이블로** 처리하고, 그 테이블이 **미검증**임을 화면·문서에 표시해야 한다.

### 1-3. 타이어(TIRE)

| 항목 | API | 반환형 [AAR] | 값 의미 | 판정 기준 |
|---|---|---|---|---|
| 바퀴 영역 | `Tire.checkWheelAreaCapabilities` | `List<WheelArea>` | 지원 바퀴 목록 | 빈 리스트면 **미지원**. 4개면 정상 [실측] |
| 저압 | `Tire.getLowTirePressure(WheelArea)` | **`Float`** | **미확정** | 앱은 `value > 0f` 이면 저압으로 본다 — **가정** |
| 공기압 | `Tire.getTirePressure(WheelArea)` | `Float` | **미확정**(kPa 추정) | 상세 표시용. 감점 계산에 쓰지 않음 |
| 경고등 | `getTelltalesInfo` TPMS | — | — | RED −50 / YELLOW −25 |

**⚠ 가장 위험한 미확정**: `getLowTirePressure`의 Float가
- (가) 저압이면 1.0, 정상이면 0.0 인 플래그인지
- (나) 실제 압력값(예: 220.0 kPa)이고 저압 판정을 앱이 해야 하는지

문서에 없어 확정 불가. **기준표 판정은 (가)를 전제로 하되, (나)일 경우를 대비해 앱이 두 경우 모두 처리하도록 요구한다.**

권장 구현: `value`가 0~1 범위면 플래그로, 100 이상이면 압력값으로 해석. 이 판별을 코드에 넣고 주석으로 근거를 남긴다.

### 1-4. 전기(ELECTRIC)

| 항목 | API | 반환형 [AAR] | 값 의미 | 판정 기준 |
|---|---|---|---|---|
| 배터리 잔량 | `EvBattery.getEvBatteryStateOfCharge` | `Int` | % (0~100) [실측: 100 반환] | **<10% → −10**. 그 외 감점 없음 |

**확정**
- SOC는 `Int`이며 % 단위다. [실측: `SOC value=100`]
- 연료와 배터리 중 **읽히는 쪽만** 쓴다. 둘 다 없으면 "잔량" 항목 측정 불가.

## 2. 권한 — API별로 무엇이 필요한가

[AAR] `PleosPermission` 상수 33종 = 읽기 11 + CONTROL 11 + PRIVATE 11.

| API 그룹 | 읽기 권한 | 비고 |
|---|---|---|
| Safety, Tire | `pleos.car.permission.CAR_SAFETY` | normal |
| EvBattery, Fuel | `CAR_ENERGY` | normal |
| Odometer, Gear, Brake, DrivingMode | `CAR_DRIVE` | normal |
| CarInfo, Display | `CAR_INFO` | normal |
| **getTelltalesInfo / registerTelltales / checkTelltalesCapabilities** | **`PRIVATE_CAR_SAFETY`** | 문서: signature\|privileged / **에뮬레이터: normal** [실측] |

**판정 기준**
- manifest에 `CONTROL_` 권한이 **0개**여야 한다.
- `PRIVATE_CAR_SAFETY`를 선언했다면 **실차에서 막힐 수 있음**을 문서에 적어야 한다.

## 3. capability(미지원) 판정 — 3가지 상태를 구분한다

평가 기준표의 "지원하지 않거나 못 읽은 값을 정상으로 처리하지 않는가"를 다음 3상태로 명확히 한다.

| 상태 | 정의 | 앱 내부 표현 | 화면 표시 | 점수 계산 |
|---|---|---|---|---|
| **지원** | capability가 정상 반환되고 값도 읽힘 | `supported=true, value!=null` | 값 또는 "정상" | 포함 |
| **미지원** | capability가 빈 목록이거나 `IllegalArgumentException(not in carPropertyConfig)` | `supported=false` | "이 차는 지원하지 않아요" | **제외** |
| **일시 실패** | capability/값 호출이 1.5초 타임아웃, 또는 그 외 예외 | `supported=true, value=null, note=timeout` | "측정 불가" | **제외**하되 "미지원"과 구분해 표시 |

**절대 규칙**
- 위 3상태 중 어느 것도 **"정상"으로 표시하면 안 된다.**
- 측정된 카테고리가 **3개 미만**이면 **등급을 내지 않는다**(`Scoring.MIN_MEASURED_CATEGORIES`).
- 카테고리 안의 모든 항목이 미지원/실패면 그 카테고리는 `null`(측정 불가).

## 4. 점수 계산 — 숫자로 확정

### 4-1. 감점표 (계획 7장)

| 원인 | 감점 | 원인 묶음(같은 묶음은 최대 1개만) |
|---|---|---|
| 화이트리스트 경고등 RED (ON·BLINK) | −50 | 경고등 type별 |
| 화이트리스트 경고등 YELLOW (ON·BLINK) | −25 | 경고등 type별 |
| 엔진오일 CRITICALLY_LOW | −50 | 엔진오일 |
| 엔진오일 LOW | −40 | 엔진오일 |
| 엔진오일 HIGH | −25 | 엔진오일 |
| 브레이크액 부족 | −40 (CRITICALLY_LOW −50, HIGH −25) | 브레이크액 |
| 타이어 저압 | **바퀴당 −20**, 바퀴 합이 1항목 | 타이어 압력 |
| 연료 <10% / 배터리 <10% | −10 | 잔량 |
| 워셔액 부족 | −10 | 워셔액 |
| 에어백 전개 | −50 | 에어백 |

- 카테고리 점수 = `max(0, 100 − Σ(원인 묶음별 최대 감점))`
- 건강 = 측정된 카테고리 평균, 종합 = 건강×0.7 + 관리×0.3
- 등급: S+ ≥95, S ≥90, A ≥80, B ≥70, C ≥60, D <60
- RED 있으면 최대 B
- **건강 문턱**: S는 건강 ≥90, S+는 ≥95일 때만. 아니면 A 상한
- 표시: 종합 **내림**, 남은 점수 **올림**

### 4-2. 데모 D3 기대값 — 재계산으로 확정 (2026-11-11)

입력: 엔진오일 NORMAL, 브레이크액 NORMAL, 바퀴 1개 저압(FL), SOC 62%, 경고등 ABS(RED)+TPMS(YELLOW), 관리 53

| 카테고리 | 계산 | 값 |
|---|---|---|
| 동력 | 100 − 0 | **100** |
| 제동·조향 | 100 − 50 (ABS RED) | **50** |
| 타이어 | 100 − 25 (**TPMS YELLOW −25가 저압 −20보다 큼. 같은 원인 묶음이므로 큰 것 하나만**) | **75** |
| 전기 | 100 − 0 | **100** |
| 안전 | 100 − 0 | **100** |
| **건강** | (100+50+75+100+100)/5 | **85.0** |
| **종합** | 85×0.7 + 53×0.3 = 59.5 + 15.9 | **75.4** |
| **등급** | 75.4 → B | **B** |
| **표시 종합** | 내림 | **75** |
| **다음 등급까지** | 80 − 75.4 = 4.6 → 올림 | **5** |

**검증 결과**: `core`의 `Demo.kt`가 `75.4 / B / 75`로 정의하고 있어 **이 계산과 일치한다.** 앱 화면도 `B · 75 · A까지 5점`을 표시했다 [실측 2026-11-11].

**핵심 규칙 확인**: 타이어에서 TPMS YELLOW(−25)와 저압 1개(−20)가 **같은 원인 묶음**이므로 **큰 감점 하나(−25)만** 적용된다. 이 규칙이 없으면 55가 되어 75가 나오지 않는다. 평가자가 이 규칙을 모르면 "왜 55가 아니지?"라고 오판한다.

### 4-3. 모든 데모 시나리오 기대값 — `core/Demo.kt` 실제 정의값

`core/src/main/kotlin/moca/core/Demo.kt` 가 정의한 값이며, `DemoHistoryTest` 가 이를 고정한다. **평가자는 이 표를 그대로 쓴다.**

| ID | 입력 | 종합(소수) | 등급 | 화면 표시 | 고정 상대 |
|---|---|---|---|---|---|
| D0 | 정상, 연료 62% | 85.9 | A | **85** | 달리는곰 |
| D1 | 엔진오일 LOW | 80.3 | A | **80** | 세차는사랑 |
| D2 | TPMS 노랑 + 바퀴 2개 저압 | 80.3 | A | **80** | 출근길요정 |
| **D3** | ABS 빨강 + TPMS 노랑 + 바퀴 1개 저압 | **75.4** | **B** | **75** | 라이벌드라이버 |
| D4 | 배터리 9% | 84.5 | A | **84** | 주말캠퍼 |
| D5 | 오일 LOW + TPMS 노랑 + 바퀴 1 저압 | 76.8 | B | **76** | 경고등수집가 |
| D6 | 타이어 미지원 | 85.9 | A | **85** | 퇴근길질주 |

**검증 방법(평가자용)**: 데모 모드를 켜고 각 시나리오에서 점검을 실행한 뒤 홈의 종합 표시값이 위 "화면 표시" 열과 같은지 본다. 다르면 실패.

**주의**: D2와 D4가 계획 10장 표(80/84)와 우연히 같아 보이지만, 계산 경로는 다르다.
- D2: 타이어 = 100 − 25(TPMS) = 75, 나머지 100 → 건강 95 → 95×0.7 + 53×0.3 = **80.3**
- D4: 전기 = 100 − 10(SOC 9%) = 90, 나머지 100 → 건강 98 → 98×0.7 + 53×0.3 = **84.5**
- D3: 제동 100−50=50, 타이어 100−25=75 → 건강 85 → 85×0.7+53×0.3 = **75.4**

## 5. 화면별 판정 기준 (모호함 제거)

### 5-1. 홈

| # | 기준 | 통과 조건(명확화) |
|---|---|---|
| 1 | 등급이 최신 점검과 같은가 | 홈 등급 == 가장 최근 점검 기록의 등급. 기록이 없으면 `—` |
| 2 | 종합·건강·관리가 맞는가 | 3개 값이 §4 공식으로 재계산한 값과 **정수까지 일치**. "다음 등급까지"는 올림 |
| 3 | 4개 버튼 이동 | 각각 점검/상태관리/보이스/대전 화면이 열림. 하단 탭과 같은 화면이면 통과 |

### 5-2. 점검하기

| # | 기준 | 통과 조건 |
|---|---|---|
| 4 | 값 5종 수신 | 오일·브레이크액·타이어·배터리·경고등 각각에 대해 **지원/미지원/일시실패 중 하나로 결과가 남아 있음**. 값이 없어도 상태가 남으면 통과 |
| 5 | 미지원을 정상으로 처리 안 함 | §3 표의 3상태 구분이 화면에 보임. `supported=false`인데 "정상" 표시가 하나라도 있으면 **실패** |
| 6 | 규칙대로 등급 | 데모 D3에서 §4-2 표와 일치 |
| 7 | 3초 이내 | 시작 시각 → 결과 표시 시각 ≤ 3.0초 [에뮬레이터 기준] |
| 8 | 기록 저장 | 점검 후 앱을 완전 종료·재실행해도 이전 점검이 남아 있음 |

**#8 현재 구현 상태 [실측: 코드 검사 2026-11-11]**: **미충족.**
- Room `@Entity`/`@Dao`/`RoomDatabase` 가 **0건**이다.
- 점검 결과는 화면에만 표시되고 **저장되지 않는다.**
- 따라서 "마지막 점검"이 항상 "아직 점검한 적이 없어요"로 나오고, 관리 점수도 항상 50(시작값)이다.
- 이 항목을 통과시키려면 Room 도입이 필요하다. **1차 제출 범위에 넣을지 결정해야 한다.**
